---
description: 指定タスクIDの実装を仕様駆動で行い、完了時にコミットする
argument-hint: <タスクID 例: PG1-2>
---

タスクID `$ARGUMENTS` の実装を、以下の手順で行ってください。

## 1. タスク特定

- タスクIDは `<プロジェクトID>-<連番>` 形式（例: `PG1-2`）。形式が不正なら理由を報告して停止する
- `docs/plan/README.md` の計画一覧でプロジェクトIDに対応する計画文書（`docs/plan/<計画名>.md`）を特定し、該当タスクのブロック（チェックボックス + 説明 + 完了条件）を探す
- タスクが見つからない場合、または既に `- [x]`（完了済み）の場合は、その旨を報告して停止する

## 2. Planモード確認

- 現在Planモードでない場合はユーザーにその旨を警告し、続行するか確認する

## 3. コンテキスト読込

実装を始める前に必ず読むこと:

- 該当タスクの説明本文と**完了条件**（多くは spec の AC 番号を参照している）
- 完了条件が参照している `docs/spec/` の該当spec（特に受入基準の章）
- `docs/implementation-rules.md`（全章。特に §2〜§5 の言語・コーディング・テスト規約と §8 のワークフロー運用）
- 必要に応じて `docs/architecture.md`・`docs/markdown-pipeline/`（Sätteriプラグイン関連タスクの場合は必読）
- 同じ計画文書内の完了済みタスクの実施履歴に、今回対応内容に関連した申し送り事項や考慮事項がないかどうか確認（必要に応じて `docs/archive/plan/` の過去計画も参照）

## 4. モデルタグ確認

タスクに `〔Fable 5〕` タグが付いている場合、現在のモデルがFable 5でなければユーザーにその旨を警告し、続行するか確認する（モデル運用ルールは `docs/implementation-rules.md` 8章を参照）。

## 5. 実装

- **仕様にない振る舞いを実装しない**。仕様の変更・詳細化が必要になったら、**先に該当specを更新**してから実装する（仕様駆動）
- implementation-rules の規約に従う: 識別子は英語・コメント/テスト名は日本語（§2）、named exportのみ・kebab-case・`any`禁止（§3）、テストは `tests/` ミラー配置で AC由来テストは `[AC-n]` 命名（§5）
- 実装中に得た知見（落とし穴・制約）は該当リファレンス文書（architecture / markdown-pipeline）へ反映する
- 必要に応じて「astro-docs」や「context7」のmcpサーバーを利用して最新の情報を取得するように

## 6. 検証

- `npm run check` と `npx astro build` を実行し、両方通ることを確認する

## 7. 進行状況更新

- 完了条件をすべて満たしたら、計画文書の該当チェックボックスを `- [ ]` → `- [x]` に更新する
- 計画内の全タスクが完了した場合のクローズ（凍結して `docs/archive/` へ移動・`docs/plan/README.md` の計画一覧の状態列更新）は、計画文書内のクローズ用タスクの指示に従う

## 8. コミット（必須）

実装完了時は必ずGitへコミットする。

- コミットメッセージ規約（`docs/implementation-rules.md` §6）:
  - Conventional Commits + 日本語サブジェクト（type: `feat` / `fix` / `docs` / `test` / `refactor` / `chore` / `content`）
  - **末尾にトレーラー `Task: <タスクID>` を必ず付与する**（例: `Task: PG1-2`）。レビューコマンドがこのトレーラーで対象コミットを収集する
- 1タスク内で意味のある単位ごとに複数コミットしてよいが、**すべてのコミットにトレーラーを付ける**
- コミット前に `npm run check` を通す

## 9. 実施内容を報告

- 該当計画文書（`docs/plan/<計画名>.md`）の `## 実施履歴` の `### <タスクID>` にて今回対応した内容の概要と特記事項があれば記載する（`## 実施履歴` セクションがまだ無い場合はタスク一覧の後に新設する）
- SSoTの原則に則り、別ドキュメントに記載した内容は該当箇所へのリンクを記載し、重複した内容を記載しないようにすること
- 概要には以下を含めること
  - 実装内容のサマリー（変更ファイル・満たした完了条件/AC）
  - 検証結果（check / build の結果）
  - 作成したコミットの一覧（ハッシュ + サブジェクト）
