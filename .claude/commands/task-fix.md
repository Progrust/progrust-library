---
description: 指定タスクIDのレビュー指摘を対応して再レビュー可能な状態にする
argument-hint: <タスクID 例: PG1-2> [対応範囲: 要修正(既定)|推奨|全部]
---

タスクID `$1` のレビュー指摘に対応してください。**新規機能の実装は行いません。レビュー指摘の解消のみを行うコマンドです**（新規実装は `/impl`、レビューは `/task-review`）。

対応範囲の指定 `$2`（省略時は `要修正`）:

| 指定 | 対応する指摘 |
| --- | --- |
| `要修正`（既定） | **要修正** のみ |
| `推奨` | **要修正** + **推奨** |
| `全部` | **要修正** + **推奨** + **軽微** |

## 1. レビュー結果の特定

- タスクIDは `<プロジェクトID>-<連番>` 形式（例: `PG1-2`）。形式が不正なら理由を報告して停止する
- `docs/archive/review/$1.md` を読む。存在しない場合は「レビュー未実施」として、先に `/task-review $1` を実行するよう案内して停止する
- ファイルに複数のレビュー結果が `---` 区切りで蓄積されている場合（再レビュー履歴）、**最後のレビューブロックのみ**を対象とする。それより前のブロックの指摘は対応済みとみなす
- 対象ブロックの `## 対応記録` に既に記載がある指摘は、**対応済みとしてスキップする**（同じ指摘を二重に直さない）

## 2. 対象指摘の抽出

- 対象ブロックの `## 指摘一覧` から、`$2` の範囲に該当する見出し（`### 要修正` / `### 推奨` / `### 軽微`）配下の指摘を抽出する
- 対象となる未対応の指摘が0件の場合は、その旨と総合判定を報告して停止する（`$2` を広げれば対応できる指摘が残っている場合はそれも伝える）

## 3. コンテキスト読込

修正に着手する前に必ず読むこと:

- `docs/plan/README.md` の計画一覧でプロジェクトIDに対応する計画文書（`docs/plan/<計画名>.md`）の該当タスクブロック（説明・完了条件・実施履歴）
- 完了条件が参照している `docs/spec/` の受入基準（AC）
- `docs/implementation-rules.md`（全章。特に §2〜§5 の規約と §7 の Definition of Done）
- 指摘が該当するファイルの現在の内容（レビュー時点から変わっている可能性があるため、行番号ではなく**現在の実際のコード**を正とする）
- 必要に応じて `docs/architecture.md`・`docs/markdown-pipeline/`

## 4. 対応方針の提示と確認

修正に入る前に、抽出した指摘ごとに以下を一覧でユーザーに提示し、**承認を得てから実装に進む**:

- 指摘の要約（重要度・該当ファイル）
- 対応方針（何をどう直すか）
- **対応しない場合はその理由**（例: レビュー後の変更で既に解消済み、仕様変更が必要で別タスクが妥当、指摘の前提が誤っている）

指摘の対応にspecの変更・詳細化が必要な場合は、**先に該当specを更新**してから実装する（仕様駆動）。specを変えずに直せない指摘は、この時点でその旨を明示して判断を仰ぐ。

## 5. 修正実装

- **指摘の解消に必要な範囲に限定する**。ついでのリファクタ・仕様にない振る舞いの追加はしない
- implementation-rules の規約に従う: 識別子は英語・コメント/テスト名は日本語（§2）、named exportのみ・kebab-case・`any`禁止（§3）、テストは `tests/` ミラー配置で AC由来テストは `[AC-n]` 命名（§5）
- 「テストが不足している」旨の指摘には、指摘されたケースのテストを追加して解消する
- 修正中に得た知見（落とし穴・制約）は該当リファレンス文書（architecture / markdown-pipeline）へ反映する

## 6. 検証

- `npm run check` と `npx astro build` を実行し、両方通ることを確認する
- 修正が既存テストを壊していないことを確認する（落ちた場合は、テストが正しいのか修正が正しいのかを判断してから直す）

## 7. コミット（必須）

- コミットメッセージ規約（`docs/implementation-rules.md` §6）:
  - Conventional Commits + 日本語サブジェクト。type は指摘の性質で選ぶ（バグ・規約違反の修正は `fix`、構造改善は `refactor`、テスト追加は `test`、文書修正は `docs`）
  - **末尾にトレーラー `Task: $1` を必ず付与する**。これにより `/task-review $1` の再レビューが今回の修正差分も収集できる
- 指摘の性質が異なる修正は、意味のある単位ごとに分けてコミットしてよい（**すべてのコミットにトレーラーを付ける**）
- コミット前に `npm run check` を通す

## 8. 対応記録の追記

`docs/archive/review/$1.md` の**対象レビューブロックの末尾**（`## 総合判定` の後）に `## 対応記録` セクションを追記する。既に存在する場合は既存内容を消さずに追記する。

- 記載内容:
  - 対応日 / 対応範囲（`$2` の値）
  - 指摘ごとの結果: **対応済み** / **対応見送り**（理由必須）。対応済みには変更内容の1行要約を付ける
  - 検証結果（check / build）
  - 作成したコミット一覧（ハッシュ + サブジェクト）
- SSoTの原則に則り、他文書に書いた内容はリンクで参照し、内容を重複させない

## 9. 進行状況の更新と報告

- 計画文書の該当タスクのチェックボックスが `- [ ]` のままで、かつ今回の修正で完了条件をすべて満たした場合は `- [x]` に更新する（既に `- [x]` の場合は操作しない）
- 計画文書の `## 実施履歴` の `### $1` に、レビュー指摘対応の概要を追記する（既存の実施履歴は消さない）
- チャットに以下を報告する:
  - 対応した指摘 / 見送った指摘の一覧
  - 検証結果
  - **`/task-review $1` で再レビューを実行するよう案内する**
